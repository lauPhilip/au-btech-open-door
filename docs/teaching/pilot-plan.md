# Pilot class plan and feedback form

This plan describes how to run Open Door with a real class for the first time and how to find out whether it works. It answers three questions: can students and the teacher use the game without help, do students learn to name threats better after playing, and what should change before the next course.

## Who takes part

One pilot class of the MSc course, with a teacher who has read the facilitator guide, and one observer who does not teach. The class plays one scenario in the 90 minute version, "Black Friday" for the first pilot, because its answer key is the best tested. A second, smaller pilot with the 45 minute version and "New bank details" follows if the first one goes well. Aim for at least fifteen students, which gives three or four teams, so that the debrief table shows real differences between teams.

## Before the class

The teacher creates the session as described in the guide and checks the join link with a phone on the classroom network. The observer prepares a stopwatch and a notes sheet with four columns: time, who, what happened and what they said. The observer sits where the teacher's screen and a few students' screens are visible and does not help. If the network fails, the class switches to the printed paper kit and the observer writes down when and why.

The students receive the information and consent text below on paper or in the course channel before they open the game, and have two minutes to read it.

## Consent and data handling

The text below is written for the students. The course owner should check it against the university's rules for pilots before it is used.

> You are invited to take part in a pilot of Open Door, a classroom game about threat modelling. Taking part is voluntary and has no effect on your grade. The game stores the first name or nickname you type, the face you pick, the team you sit in, where you walk, and the sticky notes you write. It does not ask for your surname, e-mail address or student number, and we ask you not to type any in your notes. The game deletes all of this six hours after the session starts, or earlier when the teacher closes the session. If the teacher downloads the class summary, it contains your nickname and your notes, and it is kept by the teacher for the course evaluation only. The feedback form after the class is anonymous. You may leave the pilot at any time by closing the browser, and you may take part in the class without using the game by asking the teacher for the paper version.

The game itself uses no cookies for tracking and sends no data to third parties. The only items kept in the browser are the player's name, face, team and a random identifier, so that a student who reloads the page comes back to the same place.

## What the observer watches

The observer records every point where a student or the teacher hesitates for more than ten seconds, asks someone nearby how to continue, or says that something is unclear. The observer also writes down the time when the first student has joined, when all students have a team, when the first sticky note appears, how many notes each team has when the walk ends, and how many minutes the debrief takes. These numbers show whether the timings in the guide are right and where the game needs clearer wording.

## The feedback form

The form is short and anonymous and opens on the students' own phones as the last step of the class, on a link or code the teacher writes on the board. It has two parts. The first part is the System Usability Scale, ten statements that the student answers on a five point scale from "strongly disagree" to "strongly agree". The standard wording is used and the word "system" is replaced by "game".

1. I think that I would like to use this game frequently.
2. I found the game unnecessarily complex.
3. I thought the game was easy to use.
4. I think that I would need the support of a technical person to be able to use this game.
5. I found the various parts of this game were well integrated.
6. I thought there was too much inconsistency in this game.
7. I would imagine that most people would learn to use this game very quickly.
8. I found the game very cumbersome to use.
9. I felt very confident using the game.
10. I needed to learn a lot of things before I could get going with this game.

The score is worked out in the usual way. For odd-numbered statements subtract one from the answer, for even-numbered statements subtract the answer from five, add the ten results and multiply the sum by 2.5. The average over all students is the pilot's score. A score of about 68 is average for software in general, so the target for a classroom game with no training is 75 or more.

The second part has three open questions, each with a free text box. The first asks what was the most confusing moment in the game. The second asks what the student would tell a friend that the game taught them about how companies can be attacked. The third asks what one thing should change before the next class. A last, optional question asks whether the student used a phone, a laptop or a tablet, so that problems can be linked to the device.

## After the class

The teacher and the observer meet for twenty minutes the same day and sort what happened into three piles: things that broke, things that confused, and things that worked well. Everything in the first pile becomes an issue on the project board. The SUS score and the open answers are summarised in one page that is added to the project folder with the date, the scenario, the length and the number of students. If the score is below 68, or if more than a third of the students name the same confusing moment, the next pilot waits until that moment has been fixed.

## What this plan does not do

It does not measure learning with a test. The comparison between what a team wrote and the answer key, which the game already produces, serves as the first indication, and the class summary shows how many of the reference threats each team found. A proper before and after test belongs in a later study.
